# Upstream PR #30956 (fast `ggml_sycl_comm_exchange`) on Windows, 2x B70 (2026-10-21)

[ggml-org/llama.cpp#30956](https://github.com/ggml-org/llama.cpp/pull/30956) (open, not by this repo's owner) changes
the 2-device `-sm tensor` all-reduce exchange that came upstream in #29604. Before: each device copies its half into
its own pinned host buffer, the host waits, **two CPU `memcpy`s** move the halves into a second pair of pinned buffers,
and each device uploads from its own buffer. After: each device uploads straight from the **other** device's pinned
buffer (allocated in the other queue's SYCL context), no CPU copy, and the host blocks on the uploads (needed: the
staging buffers are reused by the next call). The PR reports +16.7-20.6% tensor-split prompt speed on Linux; it gives
no decode numbers.

Tested here because cross-context host USM is not guaranteed by the SYCL spec, and on Windows Level Zero the B70s have
no peer access. In the fork both device queues are built from a `sycl::device`, so DPC++ gives them the platform's
default context; the "other context" is very likely the same context here.

## Build

Fork r67c (upstream `797de63b2` + local changes, see [REBASE-2026-10-17.md](REBASE-2026-10-17.md)). The PR's commit
does not cherry-pick (it sits on a newer upstream base, and the fork wraps the host waits in its pipeline wait-scope
helper), so it was ported by hand: same four changes, the fork's wait-scope wrappers kept on the new upload waits.
The test runtime is a copy of r67c with **only `ggml-sycl.dll` replaced** (one variable).

## Correctness

`llama-perplexity`, 8 chunks of 512 on the same text, same args as the serving entries:

| Model, 2-card `-sm tensor` | ub | r67c | r67c + PR |
|---|---|---|---|
| Mistral-Small-3.2-24B Q8_0 | 4 | 6.4583 | 6.4583 (all 8 chunks bit-identical) |
| Mistral-Small-3.2-24B Q8_0 | 512 | 6.4582, 6.4463, 6.4455 | 6.4437, 6.4435, 6.4492 |
| Mistral-Small-3.2-24B Q8_0 | 1024 | 6.4215, 6.4305 | 6.4466, 6.4338 |
| gpt-oss-120b UD-Q4_K_XL | 4 | 6.1176 | 6.1176 (all 8 chunks bit-identical) |
| gpt-oss-120b UD-Q4_K_XL | 512 | 6.0304 | 6.0371 |
| Qwen3.8-27B Q8_0 | 4 | 4.8336 | 4.8336 (bit-identical) |
| Qwen3.8-27B Q6_K | 4 | 4.8264 | 4.8264 (bit-identical) |

ub 4 is deterministic on this backend and is bit-identical. Batched tensor-split runs are not reproducible run to run
even on r67c alone (6.4455-6.4582 at ub 512), and the PR's values sit inside that spread. Fixed-answer prompts
(`bench/squal.py`) pass on every arm below. **Verdict: correct on Windows Level Zero.**

Found on the way (not caused by the PR): **`GGML_SYCL_PIPELINE=1` with `-sm tensor` makes gpt-oss-120b emit garbage**
on r67c, with or without the PR (perplexity at ub 512 fails with "negative standard deviation", the server answers
"GGGG..." and returns HTTP 500 on chat requests; ub 4 is fine). Without the pipeline variable both runtimes agree with an
older fork runtime that predates the pipeline feature (6.0308, same env). The gpt-oss tensor arms below therefore run without it; the 3-card layer arms keep it.

## Speed (A/B/B/A, `bench/arm.ps1` + `squal.py` + `sbench.py --n 512 --rounds 3 --long 30000`)

Decode = mean over rounds 2-3 of seven prompts; "30k read" = prompt tok/s on a ~31-34k-token prompt; "after" = decode
right after it. Order as run, one line per arm.

**Mistral-Small-3.2-24B Q8_0, 2 cards `-sm tensor`, 131k q4_0 KV, ub 1024 (serving entry's args):**

| Arm | Decode | 30k read | After |
|---|---|---|---|
| older runtime (b11190 fork, serving entry today) | 21.0 | 769 | 15.5 |
| r67c | 21.1 | 878 | 15.9 |
| r67c + PR | 21.7 | 1008 | 15.9 |
| r67c + PR | 21.8 | 1039 | 15.8 |
| r67c | 21.5 | 917 | 15.8 |
| older runtime | 20.4 | 857 | 15.1 |

PR vs r67c: **prompt read +14% (1024 vs 898)**, decode +2% (21.8 vs 21.3, every one of the 7 prompts moved the same way),
decode at depth equal. r67c + PR vs the older runtime: prompt +26%, decode +5%.

**gpt-oss-120b UD-Q4_K_XL (n-gram drafting on, as served):**

| Arm | Decode | 30k read | After |
|---|---|---|---|
| r67c, 3 cards `-sm layer`, 131k (serving config) | 96.3 | 1035 | 57.1 |
| r67c, 2 cards `-sm tensor` `-ts 49,51`, 80k | 39.6 | 460 | 28.8 |
| r67c + PR, 2 cards tensor | 45.8 | 475 | 27.6 |
| r67c + PR, 2 cards tensor | 42.0 | 481 | 27.7 |
| r67c, 2 cards tensor | 45.8 | 448 | 27.8 |
| r67c, 3 cards layer | 92.5 | 1030 | 54.7 |

PR vs r67c in tensor mode: prompt read +5% (478 vs 454), plain decode equal within the n-gram noise (43.9 vs 42.7;
per-prompt values swing +-30% with draft acceptance), decode at depth equal (27.7 vs 28.3). 2-card tensor stays far
behind 3-card layer either way (prompt ~2.2x, decode ~2x slower): on this EPYC host the tensor all-reduce round trips,
not the host copy the PR removes, dominate.

## Conclusion

- Correct here, and a real prompt-speed win where tensor split is used: +14% on a 24B dense model, +5% on gpt-oss-120b
  (MoE, fewer/larger all-reduces relative to compute). Smaller than the PR's +17-21% on Linux, which fits a slower
  all-reduce path on this host. Decode: +2% dense, neutral MoE.
- Only affects 2-device `-sm tensor` (the comm context is not created for other device counts or split modes), so
  layer-split entries are unaffected.
- gpt-oss-120b stays on 3-card layer split.
