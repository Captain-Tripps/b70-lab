# DeepSeek V4.1 Flash 1017: Engram conversion and first Intel run (2026-11-05)

## Status

The local GSQ-RCO IQ2_XXS pack was converted to llama.cpp's upstream DeepSeek V4.1 layout with the separate Engram tables. The converted pack loaded and generated text on the lab's four B70s using the existing llama.cpp SYCL fork. One warm run measured **1.505 tok/s decode and 10.287 tok/s prompt processing** at 2,048 context. This is a smoke test, not a validated quality or performance result. It is far below the owner's **50 tok/s minimum daily-use target**.

The prior test pack was **running without Engram**: the lab's local model loader explicitly skips ten unclaimed Engram tensors when the old GSQ-RCO format does not provide its expected PLE metadata. Its coherent output is not evidence of complete V4.1 behavior. The converted first shard has `deepseek41.ple.layers = [1, 14]`, eight heads per n-gram and embedding dimension 256; the new Engram shard indexes `per_layer_token_embd.weight` with shape [256, 768022850] and 110,595,290,400 bytes. The existing V4.1 model code builds the Engram path when the PLE metadata is present; the converted run did not emit the old skip warning. **No independent reference-logit or Engram-on/off parity test has yet been run.**

## Hardware and environment

- Native Windows, four Arc Pro B70s, driver 32.0.101.8976; EPYC 7402P, 24 cores / 48 logical processors; Windows reported approximately 112 GiB usable RAM.
- Model server: lab's `llamacpp-v41` SYCL fork, source base `de5122d` with local modifications. Production llama-swap stayed running; no production configuration was changed.
- C: and E: are partitions on a Kingston SNV3S1000G NVMe; D: is a separate WD_BLACK SN770 2TB NVMe. The old no-Engram pack was read from D:; the converted Engram-enabled pack was read from E:.
- The owner observed roughly 95% NVMe utilization during the Engram-enabled run. The device, read throughput, queue depth and latency were **not instrumented or recorded**, so this observation does not establish a storage bottleneck or identify which reads caused it.

## Exploratory no-Engram baseline

One sequential run per setting. Original four-shard pack, `-c 2048 -ngl 40 -fit off -sm layer -t 46 -lzm off -lm auto -np 1 --cache-ram 0 --no-warmup`; one `EmptyWorkingSet` call after health 200. Fixed bench-port.py prompt sequence. The split was re-solved for each CPU-expert count.

| CPU expert layers (`-ncmoe`) | `-ts` | Warm prompt tok/s | Warm decode tok/s | Generated tokens in warm decode |
|---:|---|---:|---:|---:|
| 24 | 67.5,12.5,10,10 | 12.609 | 2.320 | 128 |
| 22 | 65,12.5,12.5,10 | 13.125 | 2.334 | 107 |
| 18 | 57.5,15,15,12.5 | 15.237 | 2.730 | 110 |

The 18-layer run was about 18% faster at warm decode than this session's 24-layer run; it is a **candidate**, not a confirmed improvement. Changing `-ncmoe` also changed the layer split; these are single runs with different natural stop lengths and no variance or per-device utilization data. Short factual answers were coherent, but are not a quality evaluation. The 18-layer solver estimate was 76.50 GiB model tensor allocation across GPUs, busiest card 20.48 GiB before runtime overhead; this is not a measured peak.

## Engram conversion and run

The pack publisher's [conversion instructions](https://huggingface.co/ISTA-DASLab/DeepSeek-V4.1-Flash-1017-GSQ-RCO-GGUF#updating-an-existing-download) provide `convert_ds41_upstream.py` for the exact older four-shard format. The tested script and its small companion files were pinned to publisher revision `a419d74cd28d5b9f8c5e2b9077d11a609c17bc32`. A dry run passed. The original Engram file was copied to an isolated trial volume and its SHA-256 matched the original before conversion. The converter re-read and verified the newly written backbone tensors and rewrote only the copied Engram file's 416-byte header; it linked that copy as shard 6. The original backbone shards and original Engram file were retained. The converter reports successful completion. See the [publisher's converter](https://huggingface.co/ISTA-DASLab/DeepSeek-V4.1-Flash-1017-GSQ-RCO-GGUF/blob/a419d74cd28d5b9f8c5e2b9077d11a609c17bc32/convert_ds41_upstream.py).

The converted run retained `-ncmoe 18 -ts 57.5,15,15,12.5` and other flags above, except **`-lzm auto`**, enabling on-demand reads for the large table; it read from E: rather than D:. A trim followed readiness. It completed the same warm prompt sequence:

| Measurement | Result |
|---|---:|
| Cold decode | 1.351 tok/s, 126 output tokens |
| Warm prompt | 10.287 tok/s |
| Warm decode | 1.505 tok/s, 109 output tokens |
| End available RAM / committed memory / commit limit | 59.9 / 105.4 / 168.5 GiB |

Output included a coherent paragraph about the printing press and steam engine. This is a smoke test only. The converted run differs from the no-Engram run in **pack layout, table presence, lazy mode and physical storage device**. The two speeds cannot isolate Engram overhead or demonstrate a speed regression caused by it.

## Upstream leads

- [llama.cpp V4.1 support #31086](https://github.com/ggml-org/llama.cpp/pull/31086) is merged. [Batch splitting #31300](https://github.com/ggml-org/llama.cpp/pull/31300) is a graph-reuse improvement with CPU/CUDA validation; no B70 win is established. [Tensor-split #31447](https://github.com/ggml-org/llama.cpp/pull/31447) was open when reviewed and fixes a V4.1 tensor-split failure; it is not proof that Intel tensor split will be fast.
- [Project Maya's Intel notes](https://github.com/mw00/project-maya/blob/main/docs/INTEL_ARC.md) describe a third-party Linux result of 10.8–10.9 tok/s using three Arc cards, Maya-XS and a patched, closed-unmerged llama.cpp branch. It is a different pack, host and loader; it is not a prediction for this Windows run or evidence of a native Maya Intel engine.
- [Strata's Intel documentation](https://github.com/Niko1221/Strata/blob/main/docs/INTEL.md) said V4.1 does not run on its Intel engine when checked. The separate V4.1 SYCL port remains unmeasured and the original [Strata action plan](PLAN.md) gates have not passed because of this llama.cpp experiment.

## Next decisions

1. Profile the Engram-enabled run: simultaneous per-physical-disk throughput, read latency, queue depth and active time; CPU and per-card GPU utilization; memory, commit limit, page faults and per-run cold/warm state. Use a shared GPU lease and preserve per-sample data. Determine whether storage, CPU expert work, synchronization or placement is limiting before changing flags.
2. Compare on the **same physical storage and equivalent cold/warm conditions** where possible. The converted and old packs have different layouts and content, so a clean Engram on/off test requires a validated matching model path. Use fixed prompts, repetitions, output lengths and answer checks.
3. Validate Engram execution against an appropriate same-pack or reference path using teacher-forced logits or layer outputs, then measure representative real workloads. An independently validated complete model is a prerequisite for promoting a speed figure.
4. Assess whether a native specialized engine, expert placement/streaming, speculative decoding or hardware changes could plausibly approach 50 tok/s. Do not extrapolate the third-party Linux figure or the small `-ncmoe` improvement to that goal.

## Operational notes

The system drive became full from Remote Desktop client diagnostic traces during the session. With owner authorization, 7,771 older trace files (131.80 GiB) were moved to an archive on D:, preserving them; C: then had 133.67 GiB free and D: had 57.52 GiB free. These are point-in-time values, not capacity guarantees. The converted pack remains in an isolated trial directory on E:. Clean up only with owner direction.

The test harness held an exclusive file handle at a chosen GPU lock path and checked for known inference processes before loading. This only coordinates with processes using that same path; llama-swap remained running and a new unrelated load could still contend. Its server was stopped by PID and observed to exit; no production service was stopped.
