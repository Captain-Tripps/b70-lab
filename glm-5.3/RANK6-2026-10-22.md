# Rank 6 - IQ2_S routed-expert kernel (2026-10-22)

Operator-approved to start before the replacement CPU lands: the work is single-card and does not depend on host
RAM. Input: [LEDGER-2026-10-22.md](./LEDGER-2026-10-22.md) rank 5 - routed experts ~37% of a 94 ms verify step;
IQ2 gate/up ~197 GB/s vs IQ3_XXS down ~295 GB/s (peak ~608); limiter = IQ2_S 8 KiB grid gathered from global
memory (5 x RPS indirect loads per row vs 1 x RPS for IQ3_XXS); cost linear in tokens per window.

## Plan (written before code)

Gates (ROADMAP Phase 5): **+15% on the routed-expert operator and +3% end to end**, exact op tests for every
touched type/shape, batch-1 perplexity equal to the control build, squal identical. Randomized expert ids only.

0. **Tile sweep, no build.** `GGML_SYCL_MOE_IQ_SLM_CFG` (default 82 = 8 sub-groups x 2 rows) is read at runtime;
   it was tuned on DeepSeek shapes. Sweep 41/42/44/81/82/84 on the existing g10 binary.
1. **Tests first.** In a new worktree of the fork (`glm5-fork` @ `833f44914`, the g10 source), add GLM-exact
   `MUL_MAT_ID` cases: IQ2_S gate/up `[4096 -> 2048, 288 experts, top-8, broadcast]` and IQ3_XXS / IQ3_S down
   `[2048 -> 4096, 288, top-8]`, n = 1..8, both in eval mode (vs CPU) and perf mode.
2. **Control build** of that tree (tests only, kernels untouched) into a new runtime dir; confirm its perf matches
   the live g10 binary on the shared cases, so later deltas are the kernel, not the toolchain.
3. **One variable: compressed IQ2_S grid.** All 1024 grid entries use only bytes 0x08/0x19/0x2b, so each entry is
   16 bits of 2-bit codes (2 KiB table). Expand 4 codes -> 4 bytes with integer ops
   (`w = spread(codes); bytes = 0x08080808 + 17*w + ((w >> 1) & 0x01010101)`). Runtime switch
   `GGML_SYCL_MOE_IQ2S_GRID` = 0 (current 8 KiB global gather), 1 (2 KiB codes, global/L1), 2 (2 KiB codes in SLM),
   so one build A/Bs all three.
4. If the operator gate passes: perplexity vs control, then an arm A/B against placement A (B0), A/B/B/A.
5. Next variables only after 3 is closed: expert-reordered SoA storage for direct wide loads; weight reuse across a
   verify window.

### Correction before any code (2026-10-22, while reading the kernel)

The rank-5 verdict "the IQ2_S codebook gather is the limiter" does not hold up: the IQ2_XS kernel that was
benchmarked as the IQ2_S proxy keeps its 4 KiB grid **in SLM** (`moe_iq3_traits<IQ2_XS>::fill`), yet runs at the
same ~197 GB/s. Per **weight** the two measured kernels are close - IQ3_XXS ~770 G weights/s, IQ2_XS ~680 G
weights/s - so the cost tracks weights processed (unpack / latency / occupancy), and fewer bits per weight just
means fewer GB/s. The `indirect_stateless_count` difference is real but untested as a cause. Consequences:

- Step 3 (compressed grid) adds per-weight ALU and is now expected to lose; it is demoted below a direct IQ2_S
  measurement (step 2's control build has the exact IQ2_S perf case) and the tile sweep (step 0).
- Promoted: levers that cut per-weight work or latency - more rows per sub-group (RPS, step 0), loading weights
  straight to registers instead of the global -> SLM -> register round trip, one activation stage per work-group
  shared by more rows.

Stop conditions: two layout attempts without +8% on the exact shape, or an end-to-end ceiling under 3%.
Production is never touched: new worktree, new build dir, new runtime dir; arms on port 9078 with arm.ps1.

## Step 0 result - tile sweep (g10 binary, single card, random ids, n = 4)

`GGML_SYCL_MOE_IQ_SLM_CFG` = sub-groups x rows-per-sub-group, applied to every IQ type at once:

| cfg | IQ3_XXS down 2048->4096 | IQ2_XS gate/up 4096->2048 |
|---|---|---|
| 82 (default) | **266.5 us** | 294.2 us |
| 41 | 271.3 | 296.5 |
| 42 | 305.2 | 371.8 |
| 44 | 313.9 | 438.1 |
| 81 | 274.6 | **271.1 (-8%)** |
| 84 | 323.1 | 366.3 |

More rows per sub-group is worse (IQ2 +49% at 4 rows): each row adds its own staged-weight SLM buffer, which fits
SLM capacity limiting resident work-groups - evidence for removing the weight staging (v4), and against the
"more rows per sub-group" lever listed in the correction above. A per-type tile (81 for IQ2, 82 for IQ3) is worth
~8% on gate/up by itself and is queued as the variable after v4.

## Steps 1-3 results (fork branch `glm-r6-iq2s`: 508011862 tests, 9497abd97 v4, d3fd3818a per-type switch)

- **Control build = g10:** shared DeepSeek case IQ3_XXS n=4 266.64 us vs 266.5 us on the live g10 binary (0.05%) -
  later deltas are the kernel, not the toolchain.
- **First exact IQ2_S numbers** (GLM shape, 288 experts, top-8): n=1 97.0 us = 221 GB/s = 692 G weights/s; IQ3_XXS
  n=1 88.9 us = 289 GB/s = 755 G weights/s. IQ2_S with its grid in global memory runs at the same per-weight rate as
  IQ2_XS with its grid in SLM (682) - **confirms the correction: the grid location is not the limiter.** Routed share
  of a 94.2 ms verify step re-estimated at ~32.6 ms (~35%).
- **v4 (no weight staging, `GGML_SYCL_MOE_IQ_SLM_V=4`), 8 experts:**

| | control v3 | v4 |
|---|---|---|
| IQ2_S gate/up n=1 / n=3 | 97.0 / 317.4 us | **82.2 / 258.2 (-15% / -19%)** |

  The 98-byte IQ3_XXS blocks make the direct 16-bit reads badly misaligned; IQ2_S gains.
