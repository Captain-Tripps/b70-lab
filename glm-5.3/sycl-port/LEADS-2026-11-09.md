# GLM-5.3-Flash SYCL: optimization leads and agent handoff — 2026-11-09

**Update 2026-11-10:** L1, L2 and L4 have initial B70 screens; see the
[experiment record](experiments/2026-11-10-screening/). The remaining leads are unmeasured except where noted below.
These screens did not change the daily server.
The subsequent [resident-expert profile](experiments/2026-11-10-resident-profile/) split the prefill hotspot;
it identifies grouped gate/up and down products as the next mechanism to investigate, without proving a win.
The [grouped XMX follow-up](experiments/2026-11-10-xmx-profile/) found matrix spans dominant and approximately
53% row occupancy on the slowest card for the 8k screen, prompting a narrower-tile test.
The initial [16-row tile prototype](experiments/2026-11-10-bn16-screen/) increased occupancy but was about 17%
slower in a warmed 8k screen and is rejected at that stage; other tile mechanisms remain unmeasured.
The [64-row prototype](experiments/2026-11-10-bn64-screen/) made fewer tiles but was about 17.5% slower in its
warmed 8k screen, so it too is rejected at screening. The [48-row screen](experiments/2026-11-10-bn48-screen/)
made 13.4% fewer tiles but showed no established model speedup in its small timing sample.
The [sub-batch 768 follow-up](experiments/2026-11-10-sub768-validation/) found a repeatable four-of-64
top-token difference at 32k; the setting remains unvalidated and is not live.
The [numerical diagnosis](experiments/2026-11-10-sub768-diagnosis/) traced the first observed difference to
a batch-shaped recurrent mixer GEMM; splitting that GEMM alone did not restore 32k baseline logits.
[Selective original-size recurrent and dense batches](experiments/2026-11-10-selective-sub-batches/) left
one changed top token at 32k and showed no established speedup in a single screen.
The [partial prompt memo pilot](experiments/2026-11-10-prompt-memo-screen/) saved CPU time but did not
establish a served 115k follow-up gain in a small sample; the complete upstream port remains unmeasured.
Start here for further work on the live Maya SYCL engine. The older [llama.cpp roadmap](../ROADMAP.md) is historical;
its CPU-offload and mixed-quant priorities are not the starting point for this engine.

## Objective and scope

Improve fresh-prompt prefill, repeated agent-turn latency, and single-request decode on the existing
four-B70 Windows setup while preserving Maya-M quality and 128k operation. Keep these three measurements separate.
Prefill and prompt processing refer to the same model computation here; server-side prompt preparation is an
additional cost before that computation.

This document does not authorize publishing performance claims before measurement or changing the daily server
without a validated candidate. No engine, model, runtime, or live configuration changed during this review.

Repository reviewed at [aa5b291f](https://github.com/Captain-Tripps/b70-lab/commit/aa5b291f6234f16130bed86a3f9688257aeabe96).

Upstream reviewed through v1.1.57 at

Recheck newer changes before a backport, but do not silently change the comparison baseline.

The [port README](README.md) and [served configuration](configs/glm-maya-sycl-128k.json) are authoritative:

- Four Intel Arc Pro B70s, 32 GB each; Windows 11; EPYC 7402P; recorded driver 32.0.101.8976 and oneAPI 2026.0.
- Maya-M, all experts resident; context 131072; layer boundaries 13,24,35; the live config observed on 2026-11-10
  uses prefill chunk 768 (the earlier 1024 in this handoff and the repo example was stale); CPU lane off.
- JIT build; Level Zero v1 and immediate command lists; split MTP decode; resident-skip enabled.
- Historical short-prompt decode: 45.5–45.8 tok/s on 768-token runs.
- Historical decode after 8k: 39–40 tok/s; after 100k: 26.5 tok/s.
- Historical prefill: 966–996 tok/s at 8k and about 1,180 at 100k.
- Image prompts use the CPU encoder and reserve 400 MB. The last card needs a complete expert pool.
- The keep-alive avoids idle VRAM demotion but consumes about 0.24 GB per card. Hold its behavior constant across arms.

These numbers orient the work; they are not substitutes for a same-session baseline. The depth slowdown does
not by itself prove attention is the bottleneck: MTP acceptance, routing, residency, and pipeline balance can change.

The priority is expected investigation value, not a predicted percentage gain. L2/L3/L4 are cheaper to try than L1.

|---|---|---|---|---|

| L2 | Sweep existing DSA/MLA decode variants | Decode at depth | High: variants in pinned source; translated paths need validation | DSA sx2b4 screened, below keep gate; MLA unmeasured |

## L1 — Replace the per-head oneMKL workaround

**Evidence.** [fixups14](tools/maya_fixups14.py) replaces two interleaved strided-batch GEMMs in
[glm_prefill.cu](https://github.com/mw00/project-maya/blob/5d20b0e8/src/core/glm_prefill.cu)
with maya_gemm_heads, which calls oneMKL GEMM once per head. The original layout was rejected by oneMKL.
For the 64-head geometry, the two projections mean 128 GEMM calls per DSA sub-batch. This is a prefill issue;
do not confuse it with the older llama.cpp decode projection fix.

**Hypothesis.** Fewer submissions and more parallel head processing reduce projection wall time.

**Experiment.**
1. Confirm these calls still execute in the actual generated tree and record shapes, strides and sub-batch sizes.
2. Time query absorption and output projection separately, including gaps, at sub-batches 256/512/1024.
3. Compare the existing loop with a head-major temporary layout and a legal batched GEMM. Charge all
   gather/transpose/scatter, allocation and synchronization costs to the candidate.
4. If layout conversion consumes the gain, prototype one XMX dispatch indexed by head that reads/writes the
   original interleaved layout. Do not merely remove the original stride validation.
5. Keep an off switch, test short/tail sub-batches and actual model shapes, then benchmark whole prompts.

**Gate.** Target at least 10% lower projection wall time including conversion, and at least 3% end-to-end prefill.
If profiling bounds the possible whole-model gain below 3%, park kernel work. FP16/XMX arithmetic requires
teacher-forced quality comparison, not a claim of bit exactness.

## L2 — Existing DSA/MLA decode variants

**Evidence.** The base
[glm_fast.cu variant parser and dispatch](https://github.com/mw00/project-maya/blob/5d20b0e8/src/kernels/cuda/glm_fast.cu#L6082)
already contains STRATA_GLM_DSA_SCORE2 and STRATA_GLM_MLA_ATTN2. Defaults retain the original kernels.
No B70 sweep is documented in the published port notes.

The score variants change query storage, pools processed together and blocks per compute unit. MLA variants
change heads per block, staging and merge. Labels shown in the base include sx1b4 / rx2b4 for scores and
h16xeo / h32xvc / h64xvc for MLA. These are parser examples, not endorsed settings.

**Experiment.**
1. Inspect the translated functions and dispatch. Check that variants are implemented, not stubbed, and that
   CUDA warp intrinsics and multiprocessor counts have sensible SYCL mappings.
2. Start with a small subset of register/local-memory and staging variants. Keep score and MLA changes separate.
   Log the selected kernel; a setting that silently falls back is not a measured candidate.
3. Check operator outputs against the original path. The CUDA source intends matching arithmetic for these
   variants, but that is not proof that the translated compiler output is exact.
4. Benchmark 8k/32k/100k with fixed prompts and 768 generated tokens, both normal MTP and target-only controls.
   Use the actual port's no-spec switch after verifying its spelling and truth-value handling.
5. Record stage time, whole-step time, acceptance and pipeline head/tail balance. Validate 128k afterward.

**Gate.** Keep a configuration at >=3% geometric-mean decode gain, or >=8% on the declared deep-context workload
without a material short-context regression. If choosing by depth, make the dispatch deterministic and test
the transition. A higher acceptance rate alone is not evidence that a kernel became faster.

## L3 — Incremental server prompt preparation

**Evidence.** Maya v1.1.55 enabled MAYA_PROMPT_MEMO. The
[pinned changelog](https://github.com/mw00/project-maya/blob/00655481ce2b0689ab1c2e8d67034dc5701d6511/CHANGELOG.md)
reports about 6% less follow-up-turn time after a 115k-token GLM history on three V100s.
It preserves token IDs by preparing re-sent conversations incrementally. This is newer than the port's v1.1.44 base.

**Experiment.**
1. Diff the memoization implementation and its tests between the pinned base and reviewed upstream. Backport
   the smallest complete server change and dependencies; do not update the GPU engine wholesale.
2. Preserve the local pictures-as-text patch, CPU vision integration, chat template and API behavior.
3. Exercise memoization's verify mode against full prompt reconstruction. Cover appended tool calls/results,
   edited earlier turns, truncation, changed system prompts/tools, thinking content and alternating conversations.
   Image requests must either take a supported verified path or bypass memoization cleanly.
4. Compare memo off/on at 8k/32k/about 115k histories using append-only and edited-history turns.
5. Measure request parsing/template/tokenization separately from cache restore, fresh GPU prefill and decode.

**Gate.** Exact token-ID equivalence and a repeatable reduction in preparation/first-token latency on the declared
agent workload. GPU tok/s need not change. The upstream 6% is not a B70 forecast. Use the setting names recognized
by the backported code; older engine STRATA_ aliases and newer MAYA_ names are not interchangeable by assumption.

## L4 — Prefill sub-batches and checkpoint spacing

**Evidence.** The live config observed 2026-11-10 uses prefill chunk 768. The
[base settings](https://github.com/mw00/project-maya/blob/5d20b0e8/docs/SETTINGS.md) distinguish chunk size,
dense/attention sub-batches and conversation checkpoint boundaries. Checkpoint boundaries can drain/refill a
multi-GPU prompt pipeline. Larger sub-batches can reduce repeated weight dequantization and GEMM dispatch.

**Experiment, one variable at a time.**
1. With the actual served chunk fixed, test STRATA_GLM_PREFILL_SUB after confirming the parser and logging
   effective sub-batches. Unset defaults may already choose a large attention sub-batch.
2. Compare checkpoint intervals 16384/32768/0. The documented newer spelling is MAYA_GLM_CKPT_EVERY;
   discover the supported spelling in the actual v1.1.44-generated program/server before running.
   Interval zero disables periodic checkpoints, not necessarily all checkpoint types.
3. Keep the number of stored checkpoints and system/last-turn checkpoint policy fixed. Compare fresh prompts,
   append-only turns, edits/regeneration and cancellation/retry: fewer checkpoints can mean more recomputation.
4. Only then try larger chunks (2048 first) if measured scratch and expert-pool headroom permit.
5. Confirm complete residency before and after text and image prompts; the port has a staged-expert failure
   when scratch borrowing leaves the last pool incomplete.

**Gate.** >=3% prefill or repeatable first-token-latency improvement on the declared workload, without trading it
for worse everyday edit/retry latency or residency loss. Numerical changes from reblocking need quality checks.
Do not call reduced wall time from cache reuse an increase in fresh-token prefill throughput.

## L5 — Remaining XMX attention coverage

**Evidence.** [fixups5](tools/maya_fixups5.py) disables the CUDA tensor-core prefill DSA scorer and decode MLA
attention path. [fixups29](tools/maya_fixups29.py) implements XMX prefill attention, but does not replace those
other disabled paths.

**Experiment.**
1. Profile prefill indexer scoring and decode MLA separately at short and deep context.
2. If material, implement one missing path using joint_matrix: tiled pooled-key scoring for prefill, or
   split-over-selected-cells MLA for decode. Reuse the port's proven XMX conventions rather than CUDA assumptions.
3. Preserve causal visibility, selected-cell order, tails, softmax and split-merge semantics. For the scorer,
   compare both score error and selected pool IDs; small score changes can change the attention set.
4. Check target-only quality, MTP acceptance and whole-model wall time. Keep the original as an A/B fallback.

**Critical interaction.** fixups29 dispatches to XMX only when the latent cache is not INT8. Upstream v1.1.55
defaults to INT8 KV; importing that default can silently return this port's prefill attention to the slower
F32 path. Keep the established cache format explicit during upgrades. An INT8 experiment needs either a
compatible XMX path (for example, staged dequantization with its full cost counted) or explicit prefill regression
measurement. Do not assume the upstream CUDA INT8 performance applies here.

**Gate.** Open implementation only where the measured wall-time fraction admits >=5% end-to-end upside.
Require quality validation for changed precision. Park after two layouts fail to deliver a material model gain.

## L6 — Targeted fusion and fully resident routing

**Evidence.** The port measures roughly 7 us between dependent kernels, about 180 kernels per token per card.
[fixups19](tools/maya_fixups19.py) already gates a redundant 16 KB input copy to the host routing ring.
The [newer Strata fixes](../../strata-windows-port/slow-starts/README.md) show why hot intermediate placement
deserves inspection, but GLM is layer-split: they do not prove it has Strata's expert-parallel allocation bug.

**Experiment.**
1. Trace hot buffers' allocation type, owner, writers and readers. Separate necessary inter-card staging from
   card-local data accidentally allocated in pinned host memory.
2. For complete pools with CPU/helper lanes off, inspect the remaining route/request-ring writes, fences,
   service-thread work and fetch/wait launches. Resident-skip already exists: prove what remains before replacing it.
3. Prototype a narrow resident-only path behind a switch only if measurable overhead remains. Preserve errors,
   expert IDs/weights, cache consistency and the fallback when residency is incomplete.
4. Pick adjacent kernels for fusion only after measuring dispatch share. Preserve dependencies and recurrent state;
   do not fuse across cross-card barriers without a demonstrated ordering argument.
5. Verify the total pipeline cycle. Saving a kernel on a stage that is not limiting may yield no model speedup.

**Gate.** Exact output checks for changes intended to preserve arithmetic; >=3% model gain. Do not repeat broad
fusion or load-repacking campaigns without a new measured mechanism.

## Validation and decision rules

- Baseline A / candidate B / B / A in the same session, clean environments and no competing GPU jobs. Screen
  quickly, then validate finalists with at least 28 measured varied short-prompt samples per arm.
- Repeat depth/prefill cases at least three times per arm; distinguish a fresh prompt from a prefix-cache hit.
  Use multiple fresh starts for any allocation/residency change.
- Always report actual output counts, MTP acceptance, target/draft timing and prompt-cache reuse. Keep output
  length, thinking policy and sampling fixed. The live high-thinking config and sbench thinking-off results
  are separate workloads.
- Fixed-answer checks first. Arithmetic-preserving kernel changes need direct operator and token comparisons.
  Numerical/layout changes need teacher-forced KL/top-token checks on a fixed corpus plus long-context retrieval,
  continuation, tool-use and repetition checks. Use a declared quality budget; stop for review if none exists.
- The port's published 64-row top-20 KL comparison is a historical check, not a complete quality guarantee or
  a universal acceptance threshold. A llama.cpp-only perplexity result cannot validate a changed Maya kernel.
- Keep practical VRAM headroom and about 10 GB available host RAM under load. Record actual memory, commit,
  clocks and residency instead of relying on nominal model size.
- Complete a 30-minute mixed text/image/depth/idle soak before considering a candidate for the daily entry.
- Default keep threshold: >=3% relevant end-to-end gain above observed noise, or >=8% on a declared specialist
  workload with no material regression elsewhere. Report absolute milliseconds as well as percentages.
- No promised combined speedup: gains from these lanes may overlap.

## Do not reopen unchanged

The [rejected table](README.md#rejected) already covers generic four-card expert splitting, SYCL graph replay
under v1/immediate ordering, batched command lists that hang, int8 expert GEMM, load-time wide-load repacking,
and multi-token verification through the slow rows path. They need a changed mechanism, not another flag sweep.
Upstream CUDA-graph gains do not establish safe or fast SYCL graph replay. Faster rows kernels could eventually
justify a new MTP experiment; enabling larger windows on the existing rows implementation does not.
