# Preserving an edited conversation branch

**Early experimental result: branch revisits improved from 8.273 to 0.190 s at 8k and from about 102.2 to 0.87–0.95 s in two 115k A/B pairs, with all paired answers identical.** These are tests of a specific synthetic sequence, not whole-model throughput results or a deployable change. The live executable and configuration are unchanged.

The slot code normally removes a shorter snapshot when a newly parked state extends it. In a sequence that edits a long message, switches conversations, appends a turn, and returns to the earlier branch, the shorter reusable snapshot can disappear despite free slot capacity. The next request then reads the full prompt again. Raising the capacity to eight slots / 12 GiB alone did not eliminate the 115k reread.

An isolated build adds `STRATA_GLM_SLOT_KEEP_BRANCH=1`: for RAM slots only, retain a strictly shorter prefix snapshot instead of superseding it; exact duplicates are still removed. The flag defaults off and existing slot-count and byte limits continue to apply. [Patch](branch-preserve.patch), [8k A/B runner](branch-8k-ab.py). Both arms used the same experimental executable, four B70s, `14,25,36` split, eight slots, 12 GiB cap, 131072 context, deterministic 64-token replies, and separate fresh server processes. They ran prime → three edits → switch → return → append, then repeated the edits and switch. [Off](off-8k-requests.jsonl), [on](on-8k-requests.jsonl), with slot and memory logs alongside.

The second cycle's third edited request took **8.273 s off vs 0.190 s on**; the option-on slot log shows the 8,110-token state restored with one token left to read. Every one of the 13 corresponding outputs had the same SHA-256 hash. Six overlapping responses in the option-off build also matched a previously recorded production-runtime 8k run. Minimum available host memory during the short off/on runs was 85.67/85.58 GiB. The full sequence elapsed 51.2/43.1 s respectively. No full-logit, vision, quality, long-duration, or production test is implied.

Retaining older branches can evict other conversations sooner, and the implementation's existing byte limit is enforced after allocating the incoming snapshot; temporary memory use can exceed the cap. Slots larger than the cap can also remain as the sole entry. The option is an experiment, not a recommendation to deploy. Broader quality, vision, fairness and longer stability tests remain necessary. The separate [driver crash](../2026-11-11-trim-crash/) remains unresolved.

The first [115k A/B](branch-115k-ab.py) was interrupted after its [prime](off-115k-partial.jsonl) when a new proxy-managed GLM request arrived; the guard stopped the isolated run to free the GPUs. After the service became quiet, a fresh off/on replay completed with the same settings and sequence as the 8k test. The second cycle's third edited request took **102.200 s off vs 0.870 s on**, and all 13 paired output hashes matched. Minimum available host memory was 77.99/77.95 GiB in the off/on arms. Full sequence elapsed 243.3/142.2 s. [Off requests](off-115k-requests.jsonl), [on requests](on-115k-requests.jsonl), with slot and memory logs alongside. These are sequential single runs, not a confidence interval. The [isolated build script](build-branch.py) recompiles only the modified generated translation unit and links copied objects; adjust all `<work>` paths before reproducing.

A second fresh off/on pair reproduced the effect: the branch revisit was **102.236 s off vs 0.947 s on** and the full sequence took 243.9/142.7 s. All 13 paired answers again matched; minimum available host memory was 77.99/77.73 GiB. [Repeat off](off-115k-repeat-requests.jsonl), [repeat on](on-115k-repeat-requests.jsonl), with associated memory and slot extracts. These are two sequential pairs of one synthetic sequence, not a broad quality or production stability test.

An option-on [mixed soak](mixed-soak.py) completed **1,811.2 seconds, 98 cycles and 707 requests** on the alternate split with eight slots / 12 GiB. It included 19 intentional client disconnects followed by retries. Across 294 long edits, median TTFT was **0.908 s**, maximum **1.152 s**. Repeated identical inputs had no output-hash differences; all 49 corresponding requests from the earlier option-off mixed run also matched. Minimum system-wide available physical memory was **76.99 GiB**. [Requests](mixed-requests.jsonl), [memory](mixed-memory.jsonl), [slot log](mixed-slot-extract.log). The test did not cover vision, arbitrary tool interactions, broad quality or concurrent traffic, and the clean run does not establish that the alternate split fixes the independent Intel driver issue.

A separate 8k [image and truncation A/B](vision-ab.py) replayed the branch sequence, submitted the same llama.cpp logo image, returned to the earlier text, then submitted a truncated conversation. All **16/16 output hashes matched** between off and on, including the image, return-to-text and truncated cases. In this single pair, return-to-text TTFT was **8.176 s off vs 0.092 s on**; image TTFT was 9.487 / 9.605 s and truncation TTFT was 5.094 / 5.084 s. Minimum host available memory was 84.80 / 84.76 GiB. [Off](off-vision-requests.jsonl), [on](on-vision-requests.jsonl), [off memory](off-vision-memory.jsonl), [on memory](on-vision-memory.jsonl). This covers one image and one truncation, not general vision correctness or separate images with overlapping text.
