# Slot capacity and branch revisits — 2026-11-12

**Increasing capacity alone did not eliminate repeated 115k prompt rereads.** Two isolated runs used the experimental `14,25,36` split and RAM slots: default four slots / 8 GiB, then eight slots / 12 GiB. Both used the same deterministic mixed-conversation workload. The live config was not changed.

The four-slot run completed 49 requests over 982.2 seconds, including a client disconnect and retry; repeated identical inputs produced matching hashes. It had at least 80.07 GiB available host RAM. The eight-slot run completed 22 requests before the same Level Zero driver access violation at offset `0x4d2d87`; its minimum available host RAM was 78.20 GiB. Thus the alternative split is **not a proven driver fix**, despite its earlier clean seven-minute disk-slot run. [Driver investigation](../2026-11-11-trim-crash/).

All 22 comparable answer hashes matched between runs. The second and third cycle's third long edit each forced a full reread: **105.65 and 105.66 seconds** in the four-slot run, **102.48 and 102.45 seconds** with eight slots. These are single non-interleaved observations on a synthetic workload. The slot logs show retained states while memory was below the larger cap. Source inspection identifies another relevant behavior: when parking an extended state, `slot_put` removes a shorter prefix snapshot unless marked as an anchor or prefix. That can discard an earlier branch even with free slots. A separate [opt-in branch-preservation prototype](../2026-11-12-slot-branches/) tests the behavior.
