# IQ2_S weight-reorder lead — 2026-11-11

**Status: GPU fixture passed bit-exact comparison, but this layout was slower on the tested shape.** [llama.cpp PR #31998](https://github.com/ggml-org/llama.cpp/pull/31998) adds a reorganized layout for IQ4_NL and IQ4_XS. The general idea also applies to other quantizations: move the packed weight fields into streams better matched to GPU reads, then teach the consuming kernel how to read them. It must preserve each format's scale, index and sign semantics; a speedup for IQ4 does not establish a speedup for IQ2/IQ3.

For the B70, that PR's author reports IQ4_NL batch-1 315.9 → 70.1 µs and IQ4_XS batch-1 86.9 → 72.1 µs for a 4096×14336 matrix operation, while batch-512 timings were approximately unchanged. These are operator timings, not whole-model speedups. A Zeus GGUF-header inventory found zero IQ4_NL/XS tensors in the actual Qwen 27B Q6 file and in all three GLM Maya-M shards; the PR cannot be applied unchanged to those weights. [Inventory script](quant_probe.py).

Maya's copied grouped XMX path explicitly passes `reordered=false` in `maya_fg_shim.cpp`. Its `fg_soa` implementation supports Q8_0/Q4_K/Q5_K/Q6_K, but not IQ2_S, IQ3_XXS or IQ3_S. In the earlier [XMX profile](../2026-11-10-xmx-profile/), IQ2_S gate/up and IQ3_XXS down products dominated the measured 8k resident-expert spans, making a tailored layout a plausible test. A newer Zeus llama.cpp tree has IQ3 reorder code in other backend paths; that does not establish reordered support in Maya's copied grouped kernel or in decode.

## Prototype

The isolated [patch](iq2-planar.patch), relative to the [profiled tree](../2026-11-10-xmx-profile/) and applied with `git apply --unidiff-zero`, adds a planar IQ2_S grouped-GEMM reader and an opt-in fixture switch. For each expert it stores the exact block bytes as `[qs][qh][scales][d]`. The [fixture](xmx_iq2_reorder.cpp) creates deterministic weights and routed expert counts, transposes the bytes on the host, verifies field-by-field reversibility and runs the original or reordered grouped kernel; it records output guards, finiteness and ten timed calls after three warm-ups. The [runner](run_reorder.py) is designed to run original/reordered/reordered/original and compare full output bits, and refuses to start while llama-swap or another model occupies the GPUs.

The two fork source files and fixture compiled with zero errors, and the fixture linked. [Compile](compile-fork.out), [fixture compile](compile-fixture.out), [link](link.out). An independent [CPU byte-layout check](cpu-layout-result.txt) passed for six block counts. The GPU fixture initially waited until the separate GLM workload was idle.

With the GPUs free, the original/reordered/reordered/original fixture completed on one B70. All **1,380,352 output values matched bit-for-bit** across all four runs, with finite outputs and the fixture's guards passing. Ten timed calls per run gave median times of 0.8619, 0.8847, 0.8854 and 0.8613 ms respectively: the reordered version was about **2.7% slower** on this particular synthetic 337-row grouped operation. The measured kernel samples exclude conversion and allocation; reorder plus verification of 53,739,520 source bytes took 25.3–26.1 ms in the reordered runs. [Original 1](0-original.log), [reordered 1](1-reordered.log), [reordered 2](2-reordered.log), [original 2](3-original.log). This is a negative result for this layout and shape, not proof that every IQ2 reordering or workload is slower. No whole-model test was run.

The fixture allocates a second host copy during conversion and excludes conversion and allocation from its kernel timing. A deployable design would need to measure conversion cost, persistent host/VRAM footprint and cache behavior, and ensure **all** readers—including decode, expert staging, cache movement and grouped prefill—understand the same format or have safe separate representations. Verify no extra quantization and exact operator output where possible; then run whole-model quality and long-context gates. Production model files, runtime and config remain unchanged.

## Related device-ID PR

[#32013](https://github.com/ggml-org/llama.cpp/pull/32013) replaces a mutex-protected main-device check with a cached per-thread lookup before llama.cpp graph compute. It is a plausible Zeus Qwen/llama.cpp lead, with no measured before/after gain in its description. The older `D:\llama-master-1108` tree has the old check and its `get_current_device_id()` still delegates to the device manager. The change builds on the [#31126](https://github.com/ggml-org/llama.cpp/pull/31126) cache; replacing one call alone in that old tree would not give the advertised caching. Zeus's bundled `ggml-sycl.cpp.kvget-src` snapshot also shows the old check but describes an earlier prototype, so the exact live DLL source must be established. Multi-GPU device-selection and graph-cache correctness require careful validation. Maya's grouped shim does not call the full llama.cpp graph-compute path, so this PR does not directly address the GLM bottleneck.

## Atlas applicability

Atlas has two NVIDIA RTX 3060 GPUs and its Qwen daily driver runs the llama.cpp **CUDA** backend. The PRs above modify the SYCL backend, so neither patch is a direct CUDA change. The layout idea could still be tested in CUDA-specific kernels, but their existing implementation and performance must be measured separately; the B70 results cannot be transferred to the 3060s.

A read-only GGUF-header inventory of Atlas's running `Huihui-Qwen3.8-27B-abliterated-UD-Q4_K_XL.gguf` found **61 IQ4_XS tensors (2,698,936,320 bytes) and 6 IQ4_NL tensors (280,166,400 bytes)**, including FFN weights, as well as Q4_K, Q5_K, Q6_K, Q8_0 and other types. Thus the IQ4 format is relevant to this particular mixed-quant model despite its Q4_K filename. This does not mean the SYCL PR's implementation or its speedups apply to CUDA. Atlas's CUDA source already has IQ4-specific matrix-vector kernels; compare its current kernels first.

The Maya RAM-slot setting is part of a different server/engine and does not configure Atlas's llama.cpp server. At this inspection the two 12 GiB GPUs held about 10.1 and 10.6 GiB, and system memory was ~12 GiB available with 3.3 GiB swap in use. Those are momentary resource readings, not a safe reservation for an 8 GiB slot cache. The Atlas Qwen server was left running.

An isolated Atlas follow-up found that reducing IQ4_NL's four-column CUDA launch from four warps to two improved several synthetic operator tests on shapes present in the Qwen model. It does not test weight reordering and no whole-model gain has been measured. See the [benchmark and limitations](../../../../bench/atlas-iq4-cuda-2026-11-11/).
