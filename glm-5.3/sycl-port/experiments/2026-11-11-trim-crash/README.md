# GLM driver crash: memory-trim investigation

**Status: diagnosis narrowed; root cause and mitigation unproven.** During [RAM and disk slot tests](../2026-11-11-slot-soak/), Windows reported repeated access violations at offset `0x4d2d87` in Intel Level Zero `ze_intel_gpu64.dll` (file 1.15.39183.4, product 32.0.101.8976). The failures occurred during long-prompt prefill with both RAM and disk slot configurations; setting `ZES_ENABLE_SYSMAN=0` did not prevent a later failure.

Loading Microsoft's public DXCore symbols for the disk-control dump identified its callback as **`DXCore!DxTrimWnfCallback`**, called from a Windows thread-pool worker; the following three frames are in Intel's Level Zero driver. Both the RAM and disk dumps have the same driver offset and call stack, with a null-pointer-based read at address `0xe8`. An older slots-disabled dump also has the same named callback and driver frames. Intel private symbols are unavailable, so the nearest exported Intel symbol plus a very large offset is not the actual function name. The callback name points to memory trimming as a lead, but neither the initiating event nor the driver defect is established. Microsoft's [WDDM residency overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/driver-residency-in-wddm-2-0) describes budgets and trimming; it does not diagnose this failure.

The callback name alone does **not** establish that the GPUs exceeded a memory budget: Microsoft's [trim-notification design](https://github.com/microsoft/DirectX-Specs/blob/master/d3d/D3D12_PeriodicTrimNotifications.md) distinguishes periodic trimming from trimming to a budget. Capture the notification reason and actual per-process WDDM residency/budget before attributing this crash to pressure. Intel's public source lists a debug option to avoid registering a trim callback, but its availability in this retail Windows DLL has not been established; it was not used or proposed as a production workaround.

With the original `13,24,35` split and a 400 MiB pool reserve, the tightest B70 reported about 1,057 MiB free after loading and 0.7 GB free after the 115k prefill. A temporary 3,072 MiB reserve raised that card's startup free memory to 3,136 MiB, but the smaller expert pools hit a separate `prompt layer 14 invalid expert ID or non-finite score` error during the first prompt, so this run did not test the trim crash under a sustained load. [Server tail](reserve-3072-server.log), [engine tail](reserve-3072-engine.log), [memory](reserve-3072-memory.jsonl), [runner](reserve-control.py). An existing [handoff note](../../README.md) identifies a staged-expert correctness problem when reduced pools are borrowed for prefill; the precise relation to this layer-14 failure has not been proven.

An isolated disk-slot run shifted the split to `14,25,36`, keeping the 400 MiB reserve. All experts remained resident; startup free VRAM was 1,910 / 3,065 / 3,101 / 3,720 MiB for GPUs 0–3, and the tightest was approximately 1.5 GB after long prefill. It completed 20 requests over 434.8 seconds with no crash; all 20 comparable answer hashes matched the original-split RAM-slot run. The 115,116-token prime took 102.85 s to first token. [Requests](split-disk-requests.jsonl), [memory](split-disk-memory.jsonl), [runner](split-disk-control.py).

Subsequently the alternate split passed a 982-second, 49-request RAM-slot run, but a second alternate-split RAM run crashed at the **same** Intel driver offset after 22 requests. The second run also changed slot count and RAM cap, so it cannot isolate the split's effect; together these results show that **the alternate split is not a proven fix**. See the [slot-capacity comparison](../2026-11-12-slot-capacity/). The live service's configuration remains unchanged.
