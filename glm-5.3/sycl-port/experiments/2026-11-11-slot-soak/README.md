# Mixed slot soak — 2026-11-11

**RAM-slot soak failed early:** an isolated server using the live runtime and config with `STRATA_GLM_SLOT_RAM_GB=8` crashed during a mixed conversation-switching workload, before the planned 30 minutes completed. No live configuration was changed.

The test cycled a 115,116-token conversation through edits, a ~7,683-token conversation, return and append; periodically it added a 31,443-token conversation and two more independent conversations. It was designed to test cancellation/retry, but failed before reaching that phase. Four cycles and 28 requests completed; repeated requests with identical inputs had identical output hashes. On the next long edit, after two more conversations caused slot turnover, the engine exited partway through prefill and the HTTP stream had no content or final usage. The sampler covered about 10.1 minutes including startup; minimum available physical memory was 79.41 GiB, so the server's generic out-of-memory explanation is not supported by these samples. [Requests](ram-requests.jsonl), [memory](ram-memory.jsonl), [slot and error extract](ram-engine-extract.log), [runner](ram-soak.py).

Windows Application event reports `generate.exe` exception `0xc0000005` in `ze_intel_gpu64.dll`, driver version `1.15.39183.4`, fault offset `0x4d2d87`. An earlier slots-disabled failure produced the same exception in the same module and offset. In a disk-backed control with RAM slots disabled, the engine crashed at the same location on the initial long prefill, before any slot was saved; minimum available host memory was 86.11 GiB. [Disk control](disk-control.py), [server tail](disk-server-tail.log), [memory](disk-memory.jsonl). This weakens the case for a RAM-slot-specific trigger but does not prove the underlying cause. Do not promote the RAM setting on this evidence.

Local debugging of both new dumps showed the same null-pointer access and stack: Intel Level Zero GPU driver → DXCore → Windows thread-pool callback. The driver has export symbols only, so the debugger's nearest export name is not a reliable function identification. The driver package version reported by the DLL is `32.0.101.8976`.

As a narrow control, setting `ZES_ENABLE_SYSMAN=0` with disk slots allowed one 115k prompt to finish in 104.6 seconds, with the same output hash as the prior RAM-slot prime. [Request](sysman-off-disk-requests.jsonl), [memory](sysman-off-disk-memory.jsonl), [runner](sysman-off-disk-control.py). One pass does not demonstrate that this environment setting prevented the crash. A mixed RAM-slot run with the same setting is in progress.

The workload also exposed a performance issue: the four-slot count limit can evict a reusable long state even when the RAM byte cap has room. A later 115k edit then needed roughly 102 seconds to prefill instead of about one second with its state retained. The exact eviction sequence and whether increasing the count and budget helps require a separate controlled test.
